# AGENTS.md

Guidance for AI coding agents working in the Datadog SDK for Roku (`dd-sdk-roku`).

## Start Here

- Read [README.md](README.md) for the public API and [CONTRIBUTING.md](CONTRIBUTING.md) for human setup.
- The SDK is written in [BrighterScript](https://github.com/rokucommunity/brighterscript) (`.bs`) and compiled to BrightScript (`.brs`) by `bsc`.
- **Edit and review only `.bs` sources** (plus the `.xml` component interface files next to them). The `.brs` files under `dist/` are generated. See [Checked-in Generated Files](#checked-in-generated-files).
- **You cannot run the unit tests or the sample app.** They only run on a real Roku device. See [Testing](#testing).
- When reviewing, look for thread rendezvous costs. See [Reviewing for Rendezvous](#reviewing-for-rendezvous).

## Module Map

| Path | Content |
| --- | --- |

Consumers install the package with `ropm`, so public functions are called with the `datadogroku_` prefix (for example `datadogroku_initialize`, `datadogroku_DdUrlTransfer`).

## Build Commands

Run `npm ci` first if `node_modules` is missing.

| Command | What it does | Agent can run? |
| --- | --- | --- |
| `./tools/roku/build.sh library` | Compile `library/` into `dist/` | Yes |
| `npm run lint` | `bsc` + `bslint` build of library, test, and sample, then `cspell` on the whole repo (Markdown included) | Yes |
| `npm run check-dist` | Rebuild `dist/` and fail if it differs from `HEAD` (it runs `git add dist`) | Yes |
| `./tools/copyright/check_copyright.sh` | Check license headers | Yes |
| `npm run sca-test` / `npm run sca-sample` | Roku Static Channel Analysis; needs `ROKU_SCA` and Java 21 | Only if configured |
| `npm test` / `npm run sample` | Build, upload to `ROKU_DEV_TARGET`, and telnet to port 8085 | **No, never** |

Without a local `node_modules`, `npx --no-install` silently uses a parent directory's tool versions, so run `npm ci` first.

**Troubleshooting.** If `npm run lint` or `./tools/roku/build.sh` fails with `ENOENT … library/package.json` and the path in the error contains `***`, the checkout path has a UUID-like segment (common for agent worktrees). npm 11.x redacts it in the `npm ls --json` output that ropm parses and then opens; `npm ci` does not fix it. Run the checks in a copy whose path has no UUID-like segment: copy the tree without `node_modules`, run `git init && git add -A && git commit -m tmp` (so `check-dist` has a `HEAD`), `npm ci`, then `npm run lint` / `npm run check-dist`. Report that validation ran in a copy.

## Before You Finish

1. Run `npm run lint` and make it pass. Fix spelling in prose first; add a genuine term to `cspell.json` `words` only when needed, keeping the list sorted.
2. If anything under `library/` changed, run `./tools/roku/build.sh library` and commit the resulting `dist/` changes.
3. Make sure `git status` is clean and nothing outside your scope changed.
4. Report honestly: say that device tests were not run.

## Checked-in Generated Files

- `dist/` is generated by `bsc` (the library BrighterScript config sets `stagingDir: "../dist"`) and is committed.
- **Never hand-edit `dist/`.** Change the `.bs` (or `.xml`) under `library/` and regenerate.
- **Skip `.brs` files in review.** Use them only to map a device stack trace or line number back to the `.bs` source.
- **Regenerate and commit `dist/` before pushing** whenever `library/` changes. CI `analysis:check-dist` fails otherwise.
- `.xml` files under `library/components/` are hand-written sources, not generated.

## Code Conventions

### Public API

- Public entry points are `datadogroku_initialize`, `datadogroku_DdUrlTransfer`, the `callfunc` interfaces of `RumAgent` and `LogsAgent` (reached through `m.global.datadogRumAgent` and `m.global.datadogLogsAgent`), and the global fields in `library/globals.md`.
- A new or changed `callfunc` API needs both the `.bs` sub and a `<function name="…"/>` entry (plus any `<field>`) in the component's `.xml` `<interface>`, for example `library/components/rum/RumAgent.xml`.
- Keep the public API backward compatible. A new or changed public function or field needs a README update.
- Do not edit `CHANGELOG.md` in feature PRs; it is updated at release time.

### Threading

- **Ownership.** Every node has an owner thread, usually the Render thread. A Task thread can own non-renderable `Node` / `ContentNode` objects (and whole trees of them) that it creates. Task nodes are always Render-owned, even when created in a Task thread. Renderable (`Group`-derived) nodes need a rendezvous to be created and used from a Task thread. A Task-owned node changes owner when it is assigned to a field of, or appended as a child of, a node owned by another thread; ownership then moves to that node's owner. For example, `RumAgent.setup()` runs inside `rumAgentLoop`, creates the Node-derived `RumApplicationScope` and `RumTelemetryScope` there, and stores them in `m.top.rumScope` / `m.top.telemetryScope`, which moves them to the Render thread. `WriterTask` is a Task node, so it is Render-owned from creation. The customer-facing `RumAgent` and `LogsAgent` nodes are Render-owned.
- **Task loops.** A Task node runs its `functionName` loop (`rumAgentLoop`, `writerLoop`, `uploaderLoop`, `sendCrashReport`) on a Task thread. The Task node's `m` is cloned when the thread starts, and a message port created in `init()` only reaches the first thread launched. `RumAgent` and `WriterTask` create their port in `init()`, so never re-RUN them. `MultiTrackUploaderTask` creates its port inside `uploaderLoop()`.
- **Observers.** Callback observers (`observeField`/`observeFieldScoped(field, "callbackName")`) on fields of a Render-owned node run on the Render thread; `LogsAgent` uses these on `m.global` in `setupIfNeeded()`. Port observers (`observeFieldScoped(field, m.port)`) post `roSGNodeEvent`s to the port, handled by whichever thread `wait()`s on it. For `RumAgent` and `WriterTask` (set up in `init()`) and `MultiTrackUploaderTask` (set up in `uploaderLoop()`), that is their Task loop.
- **Event pattern.** `RumAgent`'s `callfunc` interface functions (for example `startView`) run on the Render thread and only build an event and set the matching field (`m.top.startView = …`). `rumAgentLoop` receives it on the Task thread through its port observer. Keep interface functions that thin; do the processing in the loop.
- **Never block the Render thread:** the app is killed after 10 seconds (3 seconds for sideloaded apps). Network and file I/O belong in a Task thread.
- See [Reviewing for Rendezvous](#reviewing-for-rendezvous).

### Logging and Errors

- Use the internal logger in `library/source/internalLogger.bs` (`ddLogVerbose`, `ddLogInfo`, `ddLogWarning`, `ddLogError`, `ddLogThread`), gated by the `datadogVerbosity` global field. Do not add bare `print` calls elsewhere in the library.
- Report SDK-internal errors as telemetry through `datadogRumAgent@.addErrorTelemetry` (see `fileUtils.bs`, `MultiTrackUploaderTask.bs`). Use it on error paths only: off the Render thread it costs a rendezvous.
- The SDK must never crash the host channel. Guard against `invalid` inputs from customer code.

### Static Analysis

- `bslint` rules live in `tools/lint/bslint.json` (for example, `type-annotations: all`: annotate every parameter and return type).
- CI also runs `cspell`, the copyright check, `check-dist`, and Roku SCA.

### Code Style

- Every source file starts with the 3-line Apache license header. Copy it from an existing file of the same type (`.bs` uses `'` comments, `.xml` uses `<!-- -->`).
- Follow the style of the surrounding file. Prefer small, focused functions.

## Testing

- **Unit tests and the sample app only run on a real Roku device in developer mode.** No agent can reach one. Do not try to run `npm test`, `npm run sample`, or `tools/roku/install.sh`, and never claim they ran.
- CI does not run the unit tests either: `test:roku` is manual and needs a device. Tell the user that a human has to run `npm test` on a Roku device.
- You can still write and update tests under `test/source/tests/` as `Test__*.bs`, using the helpers in `test/source/asserts` and `test/source/mock`.
- **Register new tests.** Tests are not discovered by file name. `import` a new test file in `test/components/TestRunner.bs` and add its `TestSuite__<Name>` function to `Runner.SetFunctions([...])`, otherwise it never runs.
- **Tests run on `dist/`.** The test and sample channels use the built `dist/`, which ropm copies into their `roku_modules/datadogroku` (`test/package.json` depends on `"datadog-roku": "../"`, and the root `ropm.packageRootDir` is `dist`). Library changes need a rebuilt `dist/` before tests see them; `npm run lint` does that, and also checks that the test channel compiles.

## Sample App Config

- The sample needs `sample/credentials.json`, created from `sample/credentials.json.template`. Never commit real credentials.
- Device settings (`ROKU_DEV_TARGET`, etc.) live in `.env`, created from `.env.template`. Never commit `.env`.

## Reviewing for Rendezvous

Background ([Roku threads doc](https://developer.roku.com/dev/docs/threads)): every operation a non-Render thread invokes on a Render-owned node is a **rendezvous**, a synchronous round trip that waits for the Render thread. Rendezvous slow down both the Task thread and the app UI. Review `.bs` diffs with this checklist:

1. **Count node field operations, not dots.** In Task-thread code, each get or set of a field on a Render-owned node is one rendezvous. `x.y.z` costs one per dot only while each step reads a field of a node; a dot into an associative array returned by a field is a local lookup. Reading `m.top` / `m.global` from the component's `m` is not itself a rendezvous; the field access on them is. For example, `m.global.datadogRumContext?.sessionId` in `DdUrlTransfer.bs` is one rendezvous (the `datadogRumContext` read), then a local lookup.
2. **`m.top.<field>` access in a Task thread rendezvouses.** Task nodes are owned by the Render thread, so each read or set of `m.top.<field>` from the `functionName` loop (`rumAgentLoop`, `writerLoop`, `uploaderLoop`, `sendCrashReport`) is a rendezvous.
3. **`m.global.<field>` access rendezvouses off the Render thread.** Watch reads of `datadogContext`, `datadogUserInfo`, `datadogRumContext`, `datadogVerbosity`, and similar fields inside loops.
4. **`callfunc` / `@.` on a Render-owned node from a Task thread** rendezvouses and runs the function on the Render thread, so heavy work there blocks the UI.
5. **Expect caching.** Values that rarely change (configuration, site, tokens) should be read once into a local variable or `m`. Repeated reads inside a loop or per event are a red flag.
6. **Expect batching.** Several gets or sets on the same node should use `getFields()` / `setFields()` or a single associative array field, not one call per field. Build a whole array, associative array, or node tree and hand it over once.
7. **No visual (Group) nodes in a Task thread.** Every field access on them needs a rendezvous.
8. **Callback observers run on the Render thread.** An `observeField(field, "callbackName")` on a Render-owned node (including a Task node or `m.global`) runs the callback on the Render thread; keep it short. Port observers (`observeFieldScoped(field, m.port)`) are handled by the thread that `wait()`s on the port.
9. **Non-node work is free of rendezvous.** `roUrlTransfer`, `ParseJson`, `FormatJson`, and file I/O in a Task thread are fine; the issue is only node and field access.
10. **Flag ownership transfers.** In Task-thread code, `m.top.<field> = node`, `m.global.<field> = node`, or `appendChild` onto a Render-owned parent moves a Task-created node to the Render thread. From then on, every field access or `@.` call on it from the Task thread is a rendezvous, and the `@.` call runs on the Render thread. Flag new assignments like this.
11. **Watch customer-facing hot paths.** Customer code calls `m.global.datadogRumAgent.callfunc(...)`, `m.global.datadogLogsAgent.callfunc(...)`, and `datadogroku_DdUrlTransfer` from any thread, often per frame or per request. Changes there multiply.

Precedent: CHANGELOG 1.5.0 ([#146](https://github.com/DataDog/dd-sdk-roku/pull/146), [#149](https://github.com/DataDog/dd-sdk-roku/pull/149), [#150](https://github.com/DataDog/dd-sdk-roku/pull/150), [#153](https://github.com/DataDog/dd-sdk-roku/pull/153)) cached fields and batched writes to cut rendezvous.

The `logrendezvous` command on the SceneGraph debug server (port 8080) measures rendezvous on a device. It is for humans with a device; agents should flag suspected costs in review instead.

## Branches and Commits

- Branch from `develop`. Name branches `<name>/<description>` (for example `yl/support-multi-header-types`); internal GitLab pipelines require the slash.
- Keep commits small and atomic, with a clear message that describes the change. Include the Jira key (for example `RUM-12345: ...`) when there is one.

## Pull Requests

- Target `develop` and fill in `.github/PULL_REQUEST_TEMPLATE.md`.
- Include the regenerated `dist/` when `library/` changed.
- State in the testing notes that device tests were not run by the agent.
