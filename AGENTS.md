# AGENTS.md

Guidance for AI coding agents working in the Datadog SDK for Roku (`dd-sdk-roku`).

## Start Here

- Read [README.md](README.md) for the public API and [CONTRIBUTING.md](CONTRIBUTING.md) for human setup.
- The SDK is written in [BrighterScript](https://github.com/rokucommunity/brighterscript) (`.bs`) and compiled to BrightScript (`.brs`) by `bsc`.
- **Edit and review only `.bs` sources** (plus the `.xml` component interface files next to them). The `.brs` files under `dist/` are generated. See [Checked-in Generated Files](#checked-in-generated-files).
- **You cannot run the unit tests or the sample app.** They only run on a real Roku device. See [Testing](#testing).
- When reviewing, look for thread rendezvous costs. See [Reviewing for Rendezvous](#reviewing-for-rendezvous).

## Module Map

| Path | Content |
| --- | --- |
| `library/source/` | SDK entry point (`datadogSdk.bs`, `datadogroku_initialize`), helpers, `wrapper/DdUrlTransfer.bs` |
| `library/components/core/` | `WriterTask`, `MultiTrackUploaderTask` (Task nodes), `NetworkClient` (Node) |
| `library/components/rum/` | `RumAgent`, `RumCrashReporterTask` (Task nodes), `RumScope` and its subclasses, `RumTelemetryScope` (Nodes) |
| `library/components/logs/` | `LogsAgent` (Node) |
| `library/globals.md` | Global node fields used by the SDK |
| `dist/` | **Generated** `.brs` and copied `.xml`, published to npm as `datadog-roku` |
| `test/` | Unit test channel. Tests are `test/source/tests/**/Test__*.bs`; helpers in `test/source/asserts` and `test/source/mock` |
| `test/source/testFramework/` | Vendored Roku Unit Testing Framework (third-party `.brs`). Do not edit or review |
| `sample/` | Sample channel |
| `tools/` | Build (`tools/roku`), packaging and release (`tools/repo`), lint config (`tools/lint/bslint.json`), copyright check |

Consumers install the package with `ropm`, so public functions are called with the `datadogroku_` prefix (for example `datadogroku_initialize`, `datadogroku_DdUrlTransfer`).

## Build Commands

Run `npm ci` first if `node_modules` is missing.

| Command | What it does | Agent can run? |
| --- | --- | --- |
| `./tools/roku/build.sh library` | Compile `library/` into `dist/` | Yes |
| `npm run lint` | `bsc` + `bslint` build of library, test, and sample, then `cspell` on the whole repo (Markdown included) | Yes |
| `npm run check-dist` | Rebuild `dist/` and fail if it differs from `HEAD` (it runs `git add dist`) | Yes |
| `./tools/copyright/check_copyright.sh` | Check license headers | Yes |
| `npm run sca-test` / `npm run sca-sample` | Roku Static Channel Analysis; needs `ROKU_SCA` and Java 21 | Only if configured |
| `npm test` / `npm run sample` | Build, upload to `ROKU_DEV_TARGET`, and telnet to port 8085 | **No, never** |

## Before You Finish

1. Run `npm run lint` and make it pass. Fix spelling in prose first; add a genuine term to `cspell.json` `words` only when needed, keeping the list sorted.
2. If anything under `library/` changed, run `./tools/roku/build.sh library` and commit the resulting `dist/` changes.
3. Make sure `git status` is clean and nothing outside your scope changed.
4. Report honestly: say that device tests were not run.

## Checked-in Generated Files

- `dist/` is generated by `bsc` (the library BrighterScript config sets `stagingDir: "../dist"`) and is committed.
- **Never hand-edit `dist/`.** Change the `.bs` (or `.xml`) under `library/` and regenerate.
- **Skip `.brs` files in review.** Use them only to map a device stack trace or line number back to the `.bs` source.
- **Regenerate and commit `dist/` before pushing** whenever `library/` changes. CI `analysis:check-dist` fails otherwise.
- `.xml` files under `library/components/` are hand-written sources, not generated.

## Code Conventions

### Public API

- Public entry points are `datadogroku_initialize`, `datadogroku_DdUrlTransfer`, the `callfunc` interfaces of `RumAgent` and `LogsAgent` (reached through `m.global.datadogRumAgent` and `m.global.datadogLogsAgent`), and the global fields in `library/globals.md`.
- Keep the public API backward compatible. A new or changed public function or field needs a README update.
- Do not edit `CHANGELOG.md` in feature PRs; it is updated at release time.

### Threading

- Task nodes run their `functionName` loop on a Task thread; their `init()` and any observers on their fields run on the Render thread.
- Interface functions invoked with `callfunc` run on the thread that owns the node, which is the Render thread for every SDK node.
- Never block the Render thread: the app is killed after 10 seconds (3 seconds for development builds). Network and file I/O belong in a Task thread.
- See [Reviewing for Rendezvous](#reviewing-for-rendezvous).

### Logging and Errors

- Use the internal logger (`library/source/internalLogger.bs`), gated by the `datadogVerbosity` global field. Do not add bare `print` calls in the library.
- The SDK must never crash the host channel. Guard against `invalid` inputs from customer code.

### Static Analysis

- `bslint` rules live in `tools/lint/bslint.json` (for example, `type-annotations: all`: annotate every parameter and return type).
- CI also runs `cspell`, the copyright check, `check-dist`, and Roku SCA.

### Code Style

- Every source file starts with the 3-line Apache license header (copy it from `sample/source/main.bs`).
- Follow the style of the surrounding file. Prefer small, focused functions.

## Testing

- **Unit tests and the sample app only run on a real Roku device in developer mode.** No agent can reach one. Do not try to run `npm test`, `npm run sample`, or `tools/roku/install.sh`, and never claim they ran.
- You can still write and update tests. Add them under `test/source/tests/` as `Test__*.bs`, using the helpers in `test/source/asserts` and `test/source/mock`.
- `npm run lint` compiles the test channel, so it is the check that your tests at least build.
- CI job `test:roku` is manual because it needs a device; a maintainer runs it.

## Sample App Config

- The sample needs `sample/credentials.json`, created from `sample/credentials.json.template`. Never commit real credentials.
- Device settings (`ROKU_DEV_TARGET`, etc.) live in `.env`, created from `.env.template`. Never commit `.env`.

## Reviewing for Rendezvous

Background ([Roku threads doc](https://developer.roku.com/dev/docs/threads)): every operation a non-Render thread invokes on a Render-owned node is a **rendezvous**, a synchronous round trip that waits for the Render thread. Rendezvous slow down both the Task thread and the app UI. Review `.bs` diffs with this checklist:

1. **Count the dots on nodes in Task-thread code.** `x.y.z` on a Render-owned node is one rendezvous per dot. Every field get or set is a separate rendezvous.
2. **`m.top` in a Task thread rendezvouses.** Task nodes are owned by the Render thread, so reading or setting `m.top.<field>` from the `functionName` loop (`rumAgentLoop`, `writerLoop`, `uploaderLoop`, `sendCrashReport`) is a rendezvous each time.
3. **`m.global` always rendezvouses off the Render thread.** Watch reads of `datadogContext`, `datadogUserInfo`, `datadogRumContext`, `datadogVerbosity`, and similar fields inside loops.
4. **`callfunc` / `@.` on a Render-owned node from a Task thread** rendezvouses and runs the function on the Render thread, so heavy work there blocks the UI.
5. **Expect caching.** Values that rarely change (configuration, site, tokens) should be read once into a local variable or `m`. Repeated reads inside a loop or per event are a red flag.
6. **Expect batching.** Several gets or sets on the same node should use `getFields()` / `setFields()` or a single associative array field, not one call per field. Build a whole array, associative array, or node tree and hand it over once.
7. **No visual (Group) nodes in a Task thread.** Every field access on them needs a rendezvous.
8. **Observers on Task-node fields run on the Render thread.** Keep those callbacks short; long work in them blocks the UI.
9. **Non-node work is free of rendezvous.** `roUrlTransfer`, `ParseJson`, `FormatJson`, and file I/O in a Task thread are fine; the issue is only node and field access.
10. **Watch customer-facing hot paths.** Customer code calls `m.global.datadogRumAgent.callfunc(...)`, `m.global.datadogLogsAgent.callfunc(...)`, and `datadogroku_DdUrlTransfer` from any thread, often per frame or per request. Changes there multiply.

Precedent: CHANGELOG 1.5.0 ([#146](https://github.com/DataDog/dd-sdk-roku/pull/146), [#149](https://github.com/DataDog/dd-sdk-roku/pull/149), [#150](https://github.com/DataDog/dd-sdk-roku/pull/150), [#153](https://github.com/DataDog/dd-sdk-roku/pull/153)) cached fields and batched writes to cut rendezvous.

The rendezvous logging command on the SceneGraph debug port (8080) measures rendezvous on a device. It is for humans with a device; agents should flag suspected costs in review instead.

## Branches and Commits

- Branch from `develop`. Name branches `<name>/<description>` (for example `yl/support-multi-header-types`); internal GitLab pipelines require the slash.
- Keep commits small and atomic, with a clear message that describes the change. Include the Jira key (for example `RUM-12345: ...`) when there is one.

## Pull Requests

- Target `develop` and fill in `.github/PULL_REQUEST_TEMPLATE.md`.
- Include the regenerated `dist/` when `library/` changed.
- State in the testing notes that device tests were not run by the agent.
